# Ачивки в реальной жизни

Telegram Mini App для @chb_achievements_bot. Главный экран — авторское дерево с 14 облачками и личными достижениями в корнях. Внутри ветви — прокручиваемый граф: корневой квадрат категории соединён со всеми самостоятельными ачивками, сюжетные продолжения соединены через `requires`. Все достижения можно просматривать и отмечать независимо.

Начальный каталог содержит 266 ачивок. Его ID и прежние таблицы прогресса сохранены. Дальнейшее редактирование — в базе через админку, без пересборки приложения.

## Локально

Node 22+, `npm ci`, `npm run dev`. В режиме разработки вне Telegram включается отдельное демо с localStorage и демо-админкой. Оно не обращается к пользовательской базе. В production нужен настоящий Telegram initData; параметр URL не может включить админку или демо.

`npm test` проверяет все связи каталога, ссылки, Telegram-подписи, webhook и SQL-миграции в PGlite (PostgreSQL WASM с pgcrypto). Тест базы проверяет сохранение прежних отметок, RLS двух разных пользователей, закрытые права админа, циклы и лимит 67. `npm run build` проверяет TypeScript и создаёт `dist`; `npm run lint` проверяет исходники.

## Обновление существующего проекта

Порядок важен: база и функции, затем frontend. До применения миграций новая версия покажет ошибку загрузки, а не пустой прогресс.

1. Проверить резервную копию существующей базы. Миграции 0001 и 0002 уже должны быть применены. Применить **0003_catalog_notes_admin.sql**, затем **0004_seed_catalog.sql** через Supabase SQL Editor или связанный CLI. Каждую миграцию запускать транзакционно. Не выполнять 0001 повторно поверх существующей базы.
2. Назначить владельца по его подтверждённому числовому Telegram ID через SQL Editor: `insert into public.app_admins(telegram_user_id) values (YOUR_NUMERIC_ID) on conflict do nothing;`. Не использовать username или чужой ID. Клиент не может назначать админов.
3. Развернуть `verify-init-data` и `telegram-bot` (Supabase Edge Functions, `verify_jwt=false` в config). У первой остаются существующие `TELEGRAM_BOT_TOKEN` и `APP_SIGNING_SECRET`; значение APP_SIGNING_SECRET должно совпадать с app_secrets и не должно меняться при этом обновлении.
4. У `telegram-bot` задать `MINI_APP_URL=https://saintmangle.github.io/chb-achievements-tree/` и случайный `TELEGRAM_WEBHOOK_SECRET` (допустимы A–Z, a–z, 0–9, `_`, `-`). Сохранить тот же webhook secret локально в игнорируемом `.env`. Запустить `node scripts/set-webhook.mjs`. Скрипт не удаляет ожидающие обновления Telegram. Он не предназначен для запуска до развёртывания функции.
5. После проверки базы и функций объединить изменения в main: существующий GitHub Actions публикует Pages. Для frontend нужны только VITE_SUPABASE_URL и VITE_SUPABASE_ANON_KEY из GitHub secrets. Остальные секреты никогда не попадают в сборку.
6. Проверить в настоящем Telegram: /start, старые отметки, новую отметку и заметку, личную ачивку, отправку другу, права владельца и обычного пользователя. Локальное демо не заменяет эту проверку.

Для отката интерфейса можно вернуть предыдущий frontend; новые таблицы совместимы со старым. Не удалять таблицы прогресса и личные данные. Каталог скрывается флагом active; архивирование предшественника требует сначала скрыть или перепривязать продолжения.

## Добавление ачивок

Владелец открывает «Мастерскую». Для новой ачивки: постоянный ID, категория, название, условие, необязательный предшественник, порядок. Картинка необязательна. После сохранения граф строится автоматически. ID длиной до 46 ASCII-символов сохраняет совместимость с Telegram deep links и не меняется при переименовании.

Есть предварительная проверка пакетного добавления. Формат: `ID | номер категории | название | условие | ID предшественника`; последний столбец можно оставить пустым. Можно вставить JSON-массив. Это добавление новых записей; для правок существующих предназначена отдельная форма. Новые категории появятся в переключателе. Для нового облачка сверх 14 потребуется дополнить сам рисунок и области нажатия.

## Рисунки и фоны

- `public/art/tree.png`: исходное дерево 1600×2000 с прозрачностью. Сохранить расположение облачков и пропорции — тогда достаточно заменить PNG. Если меняется композиция, подправить процентные области `treeAreas` в TreeHome.tsx.
- Текущий renderer определяет зелёные области исходного PNG и окрашивает каждое облачко отдельно. Цветные значки лучше добавлять отдельным слоем поверх дерева: зелёные пиксели внутри самой картинки могут попасть в маску листвы. При существенной смене палитры следует перейти на экспорт отдельных масок из авторского файла со слоями.
- Сохранённая доля окраски ветви не уменьшается при добавлении новых ачивок. Снятие отметки уменьшает окраску на долю одной ачивки, не ниже фактического прогресса. Цвет проявляется по постоянному узору; картинка не генерируется заново.
- Общий фон пока не подключён. Его можно добавить отдельным PNG/WebP в public/art и стилем главного экрана, независимо от дерева.
- Фон отдельной ветви уже предусмотрен полем background_url в мастерской: HTTPS или `art/имя-файла.webp`. Область графа полупрозрачная; поверх фоновых картинок остаётся затемнение для читаемости.
- Картинки ачивок — необязательное поле icon_url. Можно оформлять постепенно: без картинки отображается номер. Никаких 266 обязательных картинок.

Личные заметки и личные ачивки не включаются в ссылки «Отправить другу». Ссылка ведёт к общей ачивке через /start; бот выдаёт кнопку открытия нужной карточки.
